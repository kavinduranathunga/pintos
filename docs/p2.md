#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
In process_execute(), we use strtok_r() to get only the program name (like "grep") to create the thread. In setup_stack(), we use strtok_r() again to split the full command line (like "grep foo bar") into separate words and push each word onto the stack. While pushing strings, we save their memory addresses in a local array called argv[].   

To put argv[] in the correct order on the stack:
    1. We align the stack pointer (*esp) to a 4-byte boundary.
    2. We push a NULL pointer first.   
    3. We loop backward through our argv[] array (from the last word to the first word) and push each pointer onto the stack. This puts argv[0] at the lowest address as required by 80x86 rules.   
    4. Finally, we push the address of argv[0], argc, and a fake return address (0).

>How do you avoid overflowing the stack page?
The command line string fits inside a single 4 KB page (4096 bytes). We also limit the maximum number of words using a fixed argv[128] array so the stack frame never goes outside the user stack page


#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?
strtok() uses a global hidden variable to keep track of its position in a string. In an OS with many threads running at the same time, threads would overwrite each other's data and crash. strtok_r() uses a explicit pointer parameter (save_ptr) passed by the caller, making it safe for multiple threads to use concurrently.

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

File descriptors are unique only inside a single process, not the whole operating system.

Each program has its own private list of open files. When a program opens a file, the kernel puts it into the next empty spot on that list and returns the spot number as the file descriptor. When the program uses the file, the kernel looks up that number on the list.

Because every program has its own list, two different programs can use the same file number for different files at the same time.

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

The wait system call calls process_wait(), which looks for the specified child process.

If the child is still running: The parent waits on a semaphore inside the shared child_status structure until the child finishes.

If the child has already exited: The parent immediately reads the child's exit status from the child_status structure.

Upon process termination: When a child exits, it updates its exit status, signals the parent's waiting semaphore, and wakes up the parent. The child_status memory is carefully managed so that whichever process finishes last safely frees it.

>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

How we catch bad pointers: We check the memory address right at the start using check_buffer() or check_string(), which uses get_user() to test if the address is safe. If it is bad, the process immediately exits with -1.

How we avoid double checking: We do the full safety check once before starting any work or grabbing locks.

Cleaning up resources: Because we check pointers before touching locks or files, nothing is locked when a bad pointer happens. When the process dies, thread_exit() automatically cleans up everything.

Example: When a user calls write(fd, buffer, size), our code calls check_buffer(buffer, size) first. If buffer points to a bad address, the kernel exits immediately with -1 before acquiring the filesys_lock. Because the lock was never grabbed, no resources are left stuck or locked up.

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

When exec() is called, the parent creates the new child process and then immediately waits on a load semaphore inside our shared child_status structure. The child process runs load(). Once the child finishes loading—whether it succeeds or fails—it signals that load semaphore. This wakes up the parent, which checks whether the load was successful, returns the new process ID if it worked, or -1 if it failed.

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

We handle all of this using a shared child_status structure containing a wait semaphore and an exit status:

P waits before C exits: P blocks on the child's wait semaphore. When C exits, it records its exit status, signals the semaphore, and wakes P up.

P waits after C exits: C has already finished, signaled the semaphore, and saved its exit status, so P reads it instantly without blocking.

Resource freeing: The shared child_status struct is safely freed by whichever process (parent or child) finishes last.

P terminates without waiting: If P exits first, C can still run safely. When C eventually exits, since its parent is gone, it cleans up its own status structure so no memory is leaked.


#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

I chose to check user memory upfront using get_user() and helper functions (check_ptr, check_buffer) because it's clean, safe, and catches bad pointers before we touch any kernel locks or modify system state. It keeps the code straightforward and robust without needing complicated page-fault handler redirection.

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

Advantages: Using a fixed-size array (file_table[128]) inside each thread is very simple to write, super fast to look up using the file descriptor index, and completely isolates each process's open files.

Disadvantages: It wastes a bit of memory for processes that only open a couple of files, and it puts a hard cap of 128 on how many files a single process can have open at once.
